## 3. 真实仿真闭环及当前结果

闭环实际调用文本生成器 → 生成36D参考动作 → 官方跟踪网络/PD控制 → MuJoCo积分 → 读取实际状态 → 重采样前缀 → 再次生成。未启用 reference forcing；不是直接播放生成轨迹。

跟踪端采用自行补充的原生 PyTorch 适配器，复用官方 ScaleBFM 权重、网络核心、机器人常量和动作适配器。没有 TensorRT；规划器在GPU、跟踪器在CPU。串行离线仿真中规划会暂停物理积分，因此补充封装用**仿真时间**记录历史，单独保留真实规划墙钟耗时。它验证离线物理闭环，不能证明实时部署。

| 实验 | 实测 | 解释 |
|---|---|---|
| 静态A-pose参考跟踪 | 400次控制、8秒仿真；最低根高0.7880m | 静态跟踪稳定；不含生成规划质量 |
| 旧101更新模型，stand still，seed42 | 100次控制、400次积分、2秒仿真、12次规划；墙钟12.246秒 | 闭环确实执行完毕 |
| 同一旧模型最低根高 | 0.082927m；全程高度≥0.4m代理为false | **机器人跌倒；不能报告动作控制成功** |
| 状态→规划前缀核验 | 100个实际状态、12次规划；位置/关节误差≤5.961e-8，四元数分量误差≤4.043e-7 | 只验证反馈接线一致性，不是数据集GT评测 |

第二、三、四行使用此前单Kungfu短训模型，不代表新百万步训练的阶段结果。高度阈值是诊断代理，不是原文成功率。静态参考本身也不能作为生成模型的真值。

## 4. 后续自动执行及保存策略

服务器训练每10,000个官方step保存一次，并额外在实际更新1,000后保存恢复检查点。官方step从0开始计数，文件step999代表1,000次更新，文件step10,000代表10,001次更新。最终检查点会单独确保保存。

本地备份进程每300秒读取状态，按以下顺序处理：下载模型及优化器 → 比对服务器SHA256 → 上传GitHub Release → 核对GitHub服务端文件大小和SHA256 → 执行阶段诊断并上传报告/证据 → 按保留规则清理已确认备份的旧副本。Release是追加式上传，不覆盖不同哈希文件。

在实际更新1,000、10,001、每100k附近和最终1M，计划执行 stand still / walk forward / perform a punch 三种提示词 × seeds42/43/44，各400控制步，并对实际状态前缀做独立重采样核验。每阶段保留一个站立seed42视频。实际失败会写入失败记录，不会推断出不存在的物理指标。

六项备份单元测试使用临时虚拟字节，验证错误哈希/变更源文件/越界路径不会删除、最新副本保留、重试不改变证据包、缺少仿真回执会明确失败。这些是备份协议测试，不是机器人实验结果。

服务器保留最新检查点；本地保留最新、1,000更新和每100k里程碑的模型/优化器；GitHub保留已上传的全部检查点、阶段报告、日志与证据。此前pilot模型/优化器仅在核对GitHub备份后迁移到系统盘，原路径保留软链接，未丢弃文件。
