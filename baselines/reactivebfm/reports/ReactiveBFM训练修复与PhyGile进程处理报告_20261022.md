## 异常定位与修复

原 ReactiveBFM 约在 11,400 步出现极大梯度范数，最高记录约 2.44×10¹³，随后有非有限范数和更新拒绝。外层循环没有处理优化器失败，仍推进循环计数、学习率和 EMA。真实优化器调用计数曾停在 11,503，后来仅到 11,504，外层循环已超过 12,100。原心跳依赖成功更新数的十步间隔，导致仍显示旧的 TRAINING / 11,500，掩盖停滞。

上述控制流和监测缺陷已有日志/代码证据。BF16 数值范围与 FP32 范数归约溢出只是候选诱因，尚未唯一定位异常梯度最初的来源；不能把本次数值保护写成全部根因已证明。

本次修改：

1. FP32 前向/反向；仅范数归约与裁剪使用 FP64。
2. 优化器前后跨 rank 统一检查参数与所有优化器张量，EMA 更新前后也检查。
3. 区分优化器调用数与验证通过数；首次拒绝即停止，不再推进 EMA、学习率和保存。执行后异常明确标记“已调用、未通过”，不声称回滚。
4. 每次尝试独立记录心跳；保存配置、恢复代码及 117 个上游 Python 文件的指纹。
5. 恢复前核验完整模型/优化器对的大小、SHA256、CPU 张量和 Adam 计数；拒绝编号含义不明确的检查点。
6. 备份先验证检查点并完成 GitHub 大小/SHA256 核验，再执行评估。每个诊断前后核验模型哈希，完成绑定包含模型与回执各自的大小/SHA256。未完成绑定的旧回执保留，重试使用新目录。
7. 追踪包必须包含两个 rank 的有效终点、EMA 标记、启动和源代码记录，并内嵌检查点清单及逐文件哈希。

## 限制和后续判据

当前尚未跨过原先约11,400的异常区域，不能证明长训不再异常。FP32增加计算成本；目前短程约7–8秒/更新，若长期保持，剩余训练需要数十天。

保护器维护每步验证计数；实际10,041保存点已核验全部Adam计数一致，但尚未在每步重新断言每个Adam step。另有元数据限制：保护器full_training_completed固定false；最终完成需联合两个status文件、正常退出及已核验最终检查点确认，不能只看health字段。

1M训练、400k后课程阶段尚未完成，官方完整目标/到达数据与完整基准仍缺失。MuJoCo闭环属于仿真诊断，不代表真机或原文成绩。后续判据是：跨过原异常区间、数值有限且无跳步、检查点可恢复、GitHub新权重哈希一致、绑定检查点后的闭环与反馈验证。

独立审查使用同模型家族新代理，结论为provisional，不能表述为外部研究者独立复现。
